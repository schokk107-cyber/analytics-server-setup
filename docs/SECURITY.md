# SSH и UFW: ручные защитные шаги

Скрипт намеренно НЕ меняет `sshd_config`, НЕ запрещает root и НЕ включает UFW автоматически. Это защищает от потери SSH-доступа.

1. В панели VPS убедитесь, что доступна аварийная консоль.
2. На локальном компьютере создайте SSH-ключ (`ssh-keygen -t ed25519`).
3. Добавьте содержимое **публичного** ключа в `/home/analytics/.ssh/authorized_keys` с правами каталога `700`, файла `600` и владельцем `analytics`.
4. Задайте пароль новому пользователю командой `sudo passwd analytics`, иначе `sudo` может запросить пароль, которого у него нет. Откройте **вторую** SSH-сессию и проверьте вход под `analytics` и `sudo whoami`. Не закрывайте исходную сессию до проверки.
5. Только затем выполните `sudo ufw allow 22/tcp`, `sudo ufw default deny incoming`, `sudo ufw default allow outgoing`, `sudo ufw enable` и `sudo ufw status verbose`.
6. Проверяйте SSH ещё одной сессией. При нестандартном порте сначала разрешите **реальный** порт SSH.

Docker published ports могут обходить правила UFW: ClickHouse в шаблоне привязан только к `127.0.0.1`. Для удалённого подключения используйте SSH-туннель.

Пароль БД создаётся случайно в `/opt/clickhouse/.env`, права `600`. Не публикуйте файл. Публичный SSH-ключ безопасно хранить в репозитории только при осознанном решении; приватный ключ нельзя.

Пользователь БД `analytics` имеет широкие права для первоначальной настройки. Для DataLens создайте отдельного пользователя только для чтения.
